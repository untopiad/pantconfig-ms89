## 1. Контекст и проблематика (Context)

В процессе приёмочного тестирования функционала записи слотов DPI и назначенных им цветов на физическом устройстве PANTEON MS89 (USB VID `0x30fa`, PID `0x1440` / `0x1e01`) был зафиксирован критический дефект:
- При выполнении команды `set-dpi-slot` / `set-dpi-slots` или применении настроек через GUI значения DPI и цветовая индикация не применялись на аппаратном уровне (оставались дефолтными после ресета).
- Сопоставление дампов трафика утилиты с эталонными живыми USB-захватами официального Windows-конфигуратора выявило пять взаимосвязанных причин (root causes):

1. **Искажение старшего ниббла в цветовом энкодере:**
   Файл `src/codec/dpi.rs` формировал старший ниббл байта канала PWM из статически «замороженных» констант `COLOR_CHANNEL_HIGH_NIBBLES = [0x0, 0x1, 0xf, 0x8, 0x0, 0x0]`. В действительности старший ниббл является динамическим квантованным ШИМ второго состояния цветового эффекта/градиента.
2. **Неполная запись блока адресов `0x0030`:**
   Энкодер передавал только банки 0 и 1 (завершая 18 цветовых каналов), а банки 2..7 трактовал как незначащий padding. OEM-драйвер всегда фиксирует (latch) все 8 банков блока `0x0030`, включая ненулевые конфигурационные байты (bank 2 = `0xff`, bank 3 = `0x7f`).
3. **Отсутствие записи блока адресов `0x0038`:**
   Блок `0x0038` не формировался вовсе. OEM-драйвер передаёт блок `0x0038` из 8 банков (bank 2 = `0x0a`, bank 6 = `0x8f`).
4. **Аномальный хардкод в `execute_dpi_full_push`:**
   В `src/cli/dpi.rs` присутствовала инъекция фиктивной записи `ledger.append(ShadowEntry::new(4, 0x0010, 0x0708, ...))`, портящей регистр конфигурации DPI.
5. **Фильтрация оверлея в `build_full_push_snapshot`:**
   Функция накладывала теневой реестр (`ShadowLedger`) исключительно на фреймы, уже присутствовавшие в базовом TOML сброса (`docs/state_reset.toml`), из-за чего часть банков блоков `0x0020..0x0038` отсекалась.

## 2. Доказательная база: Тройной консенсус (Evidence)

### Канал 1. Анализ живых USB-захватов
- Механизм формирования цветового байта:
  - Функция квантования PWM: `(0xff - v + corr) >> 4`.
  - Для 18 каналов ($6 \text{ слотов} \times 3 \text{ RGB-компонента}$) наблюдаются два параллельных состояния: младшие нибблы (`lo`) и старшие нибблы (`hi`).
  - Компоновка байта: `byte = (hi << 4) | (lo & 0x0f)`.
  - В режиме частичной перезаписи обновляется только младший ниббл (`0x0f`), старший ниббл сохраняется неизменным.

### Канал 2. Эталонный USB-захват (live capture)
- Сценарий: чередование Red-Blue (`R-B-R-B-R-B`), DPI 200-400-800-1600-3200-6400, активный слот 6.
- Полный поток байтов данных (Bank 0..7) по адресам `0x0020`, `0x0028`, `0x0030`, `0x0038`:
  - `0x0020`: `00 1f ff fe 81 01 00 ff`
  - `0x0028`: `8f fe 01 b1 00 ff ff fe`
  - `0x0030`: `01 01 ff 7f 00 00 00 00`
  - `0x0038`: `00 00 0a 00 00 00 8f 00`

### Канал 3. Побайтовая валидация по live-захвату
- Сопоставление сгенерированной утилитой сессии полного применения (867 фреймов) с физической трассой `pcapng` подтвердило **0 расхождений** по всем кадрам данных и стробам фиксации блоков `0x0020`, `0x0028`, `0x0030`, `0x0038`.

## 3. Принятые решения (Decision)

1. **Двухсоставная модель кодирования нибблов (Two-State Nibble Compose):**
   - Входной интерфейс энкодера цветов расширен вторым аргументом:
     `encode_slot_colors(colors: &[(u8, u8, u8); 6], second_colors: &[(u8, u8, u8); 6]) -> Vec<WriteTransactionPlan>`.
   - Формула компоновки wire-байта:
     $$\text{wire\_byte} = (\text{rgb\_to\_pwm}(\text{second}[c]) \ll 4) \mid (\text{rgb\_to\_pwm}(\text{main}[c]) \ \& \ 0x0F)$$
   - Введена константа `DEFAULT_SECOND_COLORS` со значениями вторичных состояний каналов:
     `[(255, 238, 0), (0, 119, 255), (255, 0, 119), (0, 255, 68), (255, 0, 0), (0, 255, 255)]`.
   - Константа `COLOR_CHANNEL_HIGH_NIBBLES` помечена как устаревшая (`#[deprecated]`).

2. **Полнобанковая запись блоков `0x0030` и `0x0038`:**
   - Блок `0x0030` передаёт все 8 банков. Банки 0..1 кодируют каналы 16..17; банки 2..7 фиксируются значениями `[0xff, 0x7f, 0x00, 0x00, 0x00, 0x00]`.
   - Добавлена функция `encode_color_block_38(main, second) -> [WriteTransactionPlan; 8]`, генерирующая транзакции для банков 0..7 блока `0x0038` (bank 2 = `0x0a`, bank 6 = `0x8f` для R-B сценария).
   - Общее число транзакций цветовой сессии составляет 32 блочных плана (по 8 банков для каждого из адресов `0x0020`, `0x0028`, `0x0030`, `0x0038`).

3. **Расширение сервисного слоя (`device_service`):**
   - Добавлена публичная функция `plan_color_session(main, second) -> Vec<WriteTransactionPlan>`.
   - Существующая функция `plan_slot_colors(colors)` сохранена как deprecated-обёртка, вызывающая `plan_color_session(colors, &DEFAULT_SECOND_COLORS)`.

4. **Очистка CLI от хардкода и поддержка `edited_slot`:**
   - Удалён хардкод `(4, 0x0010, 0x0708)` из `execute_dpi_full_push`.
   - Введён параметр `edited_slot: Option<u8>`. При редактировании слота $S \in [1..6]$ регистр `ACTIVE_DPI_SLOT` (`bank 0 @ 0x0018`) автоматически обновляется значением `0x0700 | (0x18 + S - 1)`.

5. **Универсальный оверлей в `build_full_push_snapshot`:**
   - Оверлей теневого реестра применяется ко всем фреймам базового снимка с `mode == 0x03`.
   - Если в теневом реестре присутствует ключ `(bank, addr)`, отсутствующий в базовом снимке, выводится предупреждение `WARNING: ledger entry for bank ... addr ... not found in baseline snapshot; ignoring`, и операция продолжается штатно.

---

## 4. Последствия (Consequences)

### Положительные:
- Полная аппаратная применимость DPI и цветов: мышь корректно переключает индикацию и сенсор в соответствии с установленным профилем.
- Байт-в-байт совпадение формируемого wire-трафика с эталонными захватами официального драйвера.
- Исключение возможности повреждения регистра DPI случайным хардкодом.

### Обратная совместимость:
- Сигнатура публичной функции `plan_slot_colors` сохранена через `#[deprecated]`, исключая разрыв компиляции внешних потребителей.
- Новый функционал с явным указанием двух цветовых состояний доступен через `plan_color_session`.

## 6. Неразрешённые вопросы и расхождения (Unresolved)

1. **Оттенок синего цвета в эталонной трассе R-B:**
   - В эталонном live-захвате младшие нибблы слотов 2, 4, 6 (чётные слоты синего цвета) содержат значения `[0xe, 0x1, 0x1]`.
   - При декодировании формулой $v = 255 - (\text{pwm} \ll 4)$ это даёт RGB `(17, 238, 238)` (светлый морской / циан), а не чистый синий `(0, 0, 255)`, для которого младшие нибблы составили бы `[0xf, 0xf, 0x0]`.
   - Данное расхождение вызвано тем, что при снятии трассы оператор выбрал оттенок в GUI OEM-драйвера кликом по палитре, а не вводом строгих числовых значений. Формула двухсоставного кодирования математически универсальна и генерирует точные байты как для `(17, 238, 238)`, так и для `(0, 0, 255)`.
2. **Семантика параметров в блоке `0x0038` (Bank 2 = `0x0a`, Bank 6 = `0x8f`):**
   - Значения `0x0a` и `0x8f` соответствуют режиму статического свечения/дыхания DPI-подсветки, сконфигурированному в OEM Windows-драйвере при записи профиля. Зависимость этих битовых масок от альтернативных режимов подсветки (например, постоянное выключение или полноцветная волна) вынесена в будущую задачу исследования LED-режимов (M4.5).

## 7. Блочная модель фиксации (Block Session vs Per-Plan Commit)

В ходе анализа эталонных live-захватов обмена с контроллером зафиксировано строгое разграничение транзакционных моделей:
- **Per-plan commit валиден только для однобанковых блоков:** отправка пары стробов фиксации (`mode 0x09` commit + `mode 0x00` final) на каждый отдельный план допустима исключительно для изолированных однобанковых регистров.
- **Мульти-банковые блоки требуют блочной сессии (`execute_block_session`):**
  - Для блоков `0x0010` (8 банков DPI) и цветовой матрицы (`0x0020`, `0x0028`, `0x0030`, `0x0038`, по 8 банков каждый) контроллер накапливает данные всех 8 банков (`mode 0x03` для банков 0..7) и фиксирует их единым стробом `mode 0x09` (где байт 7 = `0x07` — максимальный банк) и `mode 0x00`.
  - Попытка слать per-plan commit между банками одного мульти-банкового блока сбрасывает накапливающий буфер контроллера и нарушает атомарность применения профиля.
  - Сессия блочной записи включает **единую преамбулу на сессию** (кадры разблокировки профиля на `addr 0x0001`), последовательность 8-банковых блоков и завершающий хвост (блок `0x007f`, опциональный сброс флеш-памяти `mode 0x10` и перевод в idle `mode 0x00`).

## 8. Архитектурный запрет per-plan commit для мульти-банковых блоков и Реестр блоков

Натурные испытания на физическом оборудовании (PANTEON MS89, акт M4-hf-R5) выявили критический аппаратный дефект: команды `set-polling`, `set-fire-delay` и `set-led`, писавшие одиночные банки блока `0x0018` через `execute_plans_with_commit` (per-plan commit), вызывали финализацию всего блока в контроллере мыши, перезатирая соседние регистры (`ACTIVE_DPI_SLOT`, `FIRE_DELAY`, `LED`, `POLLING`) и приводя к гибридным состояниям скорости и подсветки.

В связи с этим введено строгое архитектурное правило (Write-Gate Guard):
- Функция `execute_plans_with_commit` проверяет адрес каждого плана через предикат `is_multi_bank_block(addr)`. При попытке передачи плана с адресом мульти-банкового блока функция немедленно возвращает ошибку `PanteonError::Protocol("multi-bank block requires block session — see ADR-003 §7")`.
- Для всех операций модификации регистров мульти-банковых блоков обязательна блочная сессия (`execute_block_session`) с предварительным резолвингом полного 8-банкового блока (`resolve_block18`), сохраняющим неизменённые банки из теневого реестра (`ShadowLedger`) или снимка сброса (`docs/state_reset.toml`).

### Список мульти-банковых блоков (0x0010, 0x0018, 0x0020, 0x0028, 0x0030, 0x0038)

| Базовый адрес | Размер | Назначение и состав банков |
|---|---|---|
| `0x0010` | 8 банков | Конфигурация DPI-слотов (Bank 0..2 служебные, Bank 3 маска high-DPI, Bank 4 преамбула `0x08`, Bank 5..7 младшие нибблы DPI-значений). |
| `0x0018` | 8 банков | Системные параметры устройства:<br>• Bank 0: `ACTIVE_DPI_SLOT` (`0x0718..0x071d`)<br>• Bank 1: резерв / статус (`0x073f`)<br>• Bank 2: `FIRE_DELAY_LOW` (`delay_ms & 0xff`)<br>• Bank 3: `FIRE_DELAY_HIGH` (`(delay_ms >> 8) & 0xff`)<br>• Bank 4: `LED_EFFECT_SPEED` (режим и скорость LED)<br>• Bank 5: `LED_COLOR_PALETTE` (битовая маска палитры)<br>• Bank 6: `POLLING_RATE` (код частоты опроса `0x0700`, `0x0701`, `0x0703`, `0x0707`)<br>• Bank 7: резерв (`0x0700`). |
| `0x0020` | 8 банков | Цветовая матрица: Блок 1 (Каналы 0..7: PWM для слотов 1..3). |
| `0x0028` | 8 банков | Цветовая матрица: Блок 2 (Каналы 8..15: PWM для слотов 3..6). |
| `0x0030` | 8 банков | Цветовая матрица: Блок 3 (Каналы 16..17 + байты фиксации конфигурации `0xff, 0x7f, 0x00, 0x00, 0x00, 0x00`). |
| `0x0038` | 8 банков | Цветовая матрица: Блок 4 (Параметры эффектов подсветки, Bank 2 = `0x0a`, Bank 6 = `0x8f`). |

Все изолированные однобанковые регистры (например, `0x0008` для переназначения кнопок, `0x0070` для выбора активного профиля) остаются допустимыми для per-plan commit.

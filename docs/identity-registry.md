# Реестр аппаратных идентификаторов PANTEON MS89 и анализ реэнумерации (M2.7 / M3.1)

## 1. Реестр аппаратных идентичностей (Device Identity Registry)

| VID | PID | handshake_signature | protocol_verified | Описание и статус поддержки |
|---|---|---|---|---|
| `0x30fa` | `0x1440` | `0x0976` | **true** | Первичный (заводской) идентификатор PANTEON MS89. Протокол записи `0x18` полностью подтверждён live USB-трейсами и верифицирован на оборудовании. |
| `0x30fa` | `0x1e01` | `0x0978` | **false** | Вторичный идентификатор после реэнумерации (режим прошивки после записи и переподключения). Write-Gate Level 2 заблокирован до прохождения `verify-protocol`. |

### Архитектурные правила гейта (дополнение ADR-001):
1. **Пассивное обнаружение:** Разрешены все устройства с VID `0x30fa`, чей PID присутствует в `KNOWN_IDENTITIES`.
2. **Read-Only / Probe:** Разрешено для всех известных PID. Ожидаемая сигнатура `GET_REPORT` валидируется по полю `handshake_signature` соответствующей identity. При обнаружении неизвестного PID чтение разрешается с предупреждением.
3. **Level 2 Hardware Write:** Разрешён **только** при `identity.protocol_verified == true`. Попытка выполнить запись на неиверифицированном PID блокируется на уровне `Transport`:
   `Err(PanteonError::Protocol("protocol unverified for PID 0xNNNN — run verify-protocol first"))`.
4. **Легальная процедура верификации:** Команда `panteon-ms89 verify-protocol` — read-only пробы (handshake + дескриптор) с записью локального маркера верификации; флаги записи не требуются.

## 2. Evidence техлида: Реэнумерация PID 30fa:1440 -> 30fa:1e01

### 2.1. Исходные факты фиксации реэнумерации
* **Триггер:** После выполнения транзакции конфигурационной записи (`set-polling`) и физического переподключения (USB replug) мышь сменила PID с `30fa:1440` на `30fa:1e01`.
* **Сырой отчёт GET_REPORT (HIDIOCGFEATURE(8), Report ID 0x07):**
  ```text
  07 00 78 09 52 00 23 7b
  ```
  - Байт 0 (`0x07`): Report ID
  - Байт 1 (`0x00`): Command (Handshake / Status)
  - Байты 2..3 (`0x78 0x09`): Сигнатура `0x0978` (LE) — отличается от заводской `0x0976`
  - Байт 4 (`0x52`): Firmware revision `0x52`
  - Байт 5 (`0x00`): Зарезервировано
  - Байт 6 (`0x23`): Status byte
  - Байт 7 (`0x7b`): Flags byte

### 2.2. Опровержение гипотезы «PID кодирует polling rate»
* На новом PID `0x1e01` дескрипторы конечных точек USB в sysfs показывают:
  `/sys/bus/usb/devices/*/ep_81/bInterval = 1` -> интервал 1 мс (1000 Гц).
  `/sys/bus/usb/devices/*/ep_82/bInterval = 1` -> интервал 1 мс (1000 Гц).
* Вывод: значение PID `0x1e01` **не является** прямым битовым кодированием частоты опроса. Изменение PID связано с внутренней логикой микроконтроллера при инициализации после изменения конфигурационных регистров памяти.

## 3. Верификация гипотезы дескриптора (байты 3..4)

### 3.1. Гипотеза
В дескрипторной 32-байтовой странице байты 3..4 содержат фактический PID устройства в формате little-endian (для `0x1440` ожидались `40 14`, для `0x1e01` — `01 1e`).

### 3.2. Живые измерения на стенде
Выполнен запуск `panteon-ms89 verify-protocol -d /dev/hidraw1`:
* **Phase 1 (Probe):**
  `signature=0x0976, revision=0x54, status=0x23, flags=0x3a` (совпадает с registry для `0x1440`).
* **Phase 2 (Pre-write Descriptor):**
  ```text
  00 20 04 04 18 04 00 71 7b ef b5 d6 ff ef bf 9e ff e1 36 6b df 1f f2 fb fd f5 e7 ff f7 ee 7d df
  ```
  - Байт 1 (`unlock`): `0x20`
  - Байты 3..4: `0x04 0x18` -> LE `0x1804` (отражает эхо команды записи PackedMem `0x18`, а НЕ PID!).
* **Phase 3 (Write Test 1000 Hz):**
  `07 18 09 00 01 00 05 00` -> `07 18 00 00 01 00 07 00` -> `07 18 03 06 18 00 00 07` -> `07 18 09 00 01 00 00 00` -> `07 18 00 00 01 00 00 00`.
  Interrupt IN ACK подтверждён.
* **Phase 4 (Post-write Descriptor):**
  ```text
  03 20 04 04 18 04 00 71 7b ef b5 d6 ff ef bf 9e ff e1 36 6b df 1f f2 fb fd f5 e7 ff f7 ee 7d df
  ```
  - Байт 0 изменился на `0x03` (Interrupt IN ACK type echo).
  - Байт 6 (`write_echo`): `0x00` (младший байт слова `0x0700`).

### 3.3. Вывод по гипотезе
Байты 3..4 дескриптора **не содержат** аппаратный PID. Это рабочие регистры контроллера / эхо адресации.
Единственным надёжным источником PID является дескриптор USB устройства в ядре (`sysfs: /sys/class/hidraw/*/device/uevent`).

## 4. Матрица M3.1: Чеклист исследования реэнумерации при replug

Так как USB-переподключение требует физического отключения кабеля пользователем, данные не симулируются. Чеклист предназначен для пошаговой фиксации измерений:

### Методика проведения эксперимента:
1. Запись частоты: `panteon-ms89 set-polling <rate> -d /dev/hidraw1 --confirm --write`
2. Физическое отключение USB-кабеля мыши от порта ПК (пауза 3 сек).
3. Подключение кабеля обратно.
4. Фиксация VID:PID через `lsusb -d 30fa:`.
5. Проверка интервала опроса: `cat /sys/bus/usb/devices/*/ep_81/bInterval` и `ep_82/bInterval`.
6. Выполнение `panteon-ms89 probe -d /dev/hidraw1 --read` с фиксацией сигнатуры и ревизии.
